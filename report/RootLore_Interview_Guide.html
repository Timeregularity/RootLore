1. Project foundation

Simple first

GitHub answers are often scattered across old issues, maintainer comments, docs and releases. RootLore collects a small relevant set, asks an LLM to reason only over it, then checks the model’s citations and risky claims before showing an answer. If it cannot support a fix, it improves the report and asks for missing diagnostics.

Interview-ready definition

RootLore is a multi-interface retrieval-augmented issue assistant. A React/Vite web app or Chrome MV3 extension calls an Express API. The API retrieves bounded GitHub evidence, ranks it lexically, sends selected context to Groq’s openai/gpt-oss-20b under a strict JSON Schema, and deterministically validates the generated result.

4. End-to-end analysis flow

  1. User enters a GitHub URL, title and description; the web UI parses owner/repository. Extension can also send issueNumber.
  2. POST /api/repositories/:owner/:repository/analyze; params come from URL, body from parsed JSON.
  3. Limiter counts the client IP; validation checks name regex, strings, non-empty text, title ≤200, description ≤10,000.
  4. Fetch recent issues (≤100), optional older search (≤20), and optional current issue; remove duplicates by issue number.
  5. Extract ≤3 explicit file paths and rank issues; current issue is forced in, total evidence issues ≤3.
  6. Promise.all concurrently enriches selected issues plus releases, docs and named files. Optional failures become [].
  7. Rank docs/source; combine command corrections + files + docs, deduplicate, slice to ≤4 passages.
  8. Groq receives bounded evidence and strict schema. Provider JSON is parsed, citations/claims are validated, and an outcome is chosen.
  9. API returns evidence, optimization counts, model metadata and analysis; UI renders and stores last 10 analyses locally.
Async interview point
await pauses this async function without blocking Node’s process. Promise.all overlaps independent I/O. Removing await would pass unresolved Promises or return too early; one rejection rejects the group, but optional calls are wrapped to resolve as empty arrays.

5. RAG from zero

Three verbs

Retrieve

Find relevant repository evidence.

Augment

Add that evidence to the model prompt.

Generate

Create a structured answer grounded in it.

Grounding ties claims to supplied evidence. Hallucination is unsupported generated content. A context window is the model’s limited input capacity. Retrieval quality determines whether useful evidence reaches it.

Why RootLore qualifies

It retrieves issues, comments, timelines, releases, documentation and explicit files before generation, selects relevant evidence locally, and injects it into the Groq request. It is RAG without vectors.

Actual retrieval type: lexical

Words are lowercased, tokenized (≥3 chars), stop words removed, and simple plural endings normalized. Issue score weights title ×3, labels ×2, body ×1 and exact errors ×4; score threshold is 15%. Documents score shared terms plus 3 for numbers within 5%.

Why no embeddings?
For an MVP, lexical scoring was explainable, deterministic, dependency-light and easy to regression-test. The trade-off is missing semantic matches with different vocabulary. Add embeddings later by chunking docs/issues, storing vectors with metadata, retrieving top-k semantic results, then combining normalized lexical and vector scores—while retaining exact-quote validation.

7. Groq and structured generation

Provider/model: POST https://api.groq.com/openai/v1/chat/completions, model openai/gpt-oss-20b, temperature 0.2, max completion 2,200 tokens, timeout 30s.

Input bounds: current issue body 1,000 chars/last 6 comments ×400; other bodies 600/last 3 comments ×300; last 3 timeline events; 3 releases ×400; 4 passages ×600; submitted description sent at ≤5,000 although route accepts ≤10,000.

Schema: summary, improved title/report, questions, duplicate, suggested solution, confidence, issue claims and documentation claims. strict: true reduces parsing ambiguity; local shape checks remain.

Failures: network/timeout →503; non-JSON or invalid shape →502; provider HTTP status preserved. A valid JSON object inside error.failed_generation can be recovered with conservative defaults, then fully validated.

Cache: SHA-256 of report + evidence versions, 24h TTL, ≤250 entries, concurrent identical requests share one Promise.

Could it work without AI?
Partly. Ranking, duplicate candidates, deterministic command correction, quality scoring and issue templates can work without AI. The LLM adds synthesis, cautious inference, follow-up questions and natural rewriting. A non-AI fallback would be less flexible but more predictable.

8. Hallucination controls

  • Evidence-only prompt: repository text is declared untrusted and cannot override system instructions.
  • Allow-list: issue numbers and document paths must exist in the supplied evidence.
  • Exact quote: normalized quote length ≥12 and must be a substring of matching evidence.
  • Duplicate: needs a validated claim marked duplicate; current issue cannot match itself.
  • Closure: closed + not not_planned + final closer’s comment says fixed/resolved/worked; closure alone is insufficient.
  • Versions: suggested solution cannot introduce version tokens absent from report/evidence.
  • Risk: low-confidence destructive/state-changing verbs are blocked without solution evidence.
  • Improved report: invented environment, reproduction steps and errors are removed; retrieved facts cannot impersonate reporter observations.
  • Context vs decision: summary-only claims are relabeled as similarity and capped at two; they do not verify cause.
Unsupported claim→validator rejects quote/version/action→downgrade/remove→safe outcome
Why prompt rules are insufficient
Models can misunderstand, ignore instructions, or return malformed/crafted content. Deterministic checks are a second, testable boundary. They reduce—not eliminate—hallucination and prompt-injection risk.

9. API interview table

Method + routePurpose / inputValidation + limitResponse / failures
GET /healthLiveness; no params/bodyNo analysis limiter200 {status:'ok'}
GET /api/repositories/:owner/:repository/issuesNormalized issues; URL paramsName regex; no custom rate limit200; 400 invalid; GitHub status or 500

Status reasoning

POST carries a report and triggers a composed analysis; GET reads a resource. 400 means client input is invalid. 404 is used by unknown local routes or can pass from GitHub. 429 protects quota. 500 is unexpected server failure; 502 invalid provider output; 503 missing Groq key, timeout or unreachable upstream.

How to secure further
Add authentication/authorization, stricter extension-origin allow-list, request body size at parser level, proxy trust configuration, distributed rate limiting, audit logs, secret manager, outbound allow-list, prompt-injection red teaming and abuse monitoring.

Multiple backend instances
Each instance has separate cache and limiter state, so hit rate drops, duplicate upstream calls occur, and a client can receive more total allowance. Use Redis (or another shared TTL store) for cached data, locks/request coalescing and atomic distributed counters.
Stale cache
Expired entries are not immediately deleted. A later request revalidates with ETag; if unchanged, GitHub returns 304 and the cached data becomes fresh.

RootLore solves GitHub issues using repository evidence rather than generic model memory. A React app or Chrome extension sends a report to Express.
